# Phase 0 研究：变量与表格数据源

本文记录实现前必须定下的技术决策。每条包含**结论**、**理由**、**否决的替代方案**。
规格层面的取舍已在 `spec.md` 与 `docs/variables-and-data-sources.md` 中，这里只谈实现。

---

## R1. `${}` 解析器：自建，不引依赖

**结论**：在 `@zenith/shared` 中实现一个约 60 行的扫描器，输出「字面片段 / 引用」的
序列。不引入模板引擎。

**理由**：文法只有两条规则（`${`…`}`、`$${` 转义），且必须与渲染器共用同一个实现——编辑器画的和打印机烧的必须来自同一次
解析。通用模板引擎会带来条件、循环、过滤器等我们明确不要的东西，而它们一旦可用就会
被用上。

**否决**：Mustache / Handlebars —— 语法更宽，且 `{{}}` 与我们已冻结的 `${}` 不符；
正则一把梭 —— 无法正确处理 `$${` 的配对（`$$${sku}` 要先配 `$$` 再认引用），且错误
位置无法定位（FR-014 需要指出是哪个引用无法解析）。

**后续简化**：文法原本还有「以第一个 `.` 分路径」与「引号段包裹含点号的列名」两条，
随两级路径 `${源.列}` 一并取消——见 `contracts/variable-grammar.md` 的「为什么没有
`${源.列}`」。扫描器因此更短，且列名里的点号不再需要用户操心。

**测试形态**：纯函数，`parse(content) → Segment[]`，无 DOM、无 IO。属于宪章
「纯逻辑 MUST 抽离并直接测试」的范畴。

## R2. 编码探测：Node 自带，无需依赖

**结论**：用 `TextDecoder` 解码，候选顺序为 UTF-8（含 BOM 判定）→ GB18030 → Big5。
以「解码后不含替换字符 U+FFFD 且中文字符占比合理」为判定。用户可手工指定后重试。

**理由**：已实测 Node 26 自带 full ICU，`new TextDecoder('gbk' | 'gb18030' | 'big5')`
均可用，`d6 d0 ce c4` 正确解出「中文」。引入 iconv-lite 只是把已有能力再装一遍，而
宪章要求原生模块依赖必须有理由。

**否决**：iconv-lite（重复既有能力）；只支持 UTF-8（中文 Excel 导出的 CSV 常为 GBK，
FR-022 已要求支持）。

---

## R3. 分隔符探测：数首行

**结论**：在候选 `,`、`;`、`\t` 中，取在**表头行**里（引号外）出现次数最多者。全为 0
时按逗号处理，随后表头校验会给出明确失败。

**理由**：表头行几乎不含引号内的分隔符，计数极可靠且实现只有几行。

**否决**：整文件统计（大文件昂贵，且数据行里的分隔符会干扰）；只认逗号（FR-022a 已
要求支持分号）。

---

## R4. CSV 解析：自建最小实现

**结论**：自建，支持 RFC 4180 的引号规则（`""` 转义引号、引号内可含分隔符与换行）与
`\r\n` / `\n` 两种行尾。

**理由**：需求面窄且明确，而 papaparse 之类会带来流式、动态类型推断、header 变换等
特性——**其中类型推断正是 FR-024 明确禁止的**，默认开启时会把 `007` 变成 `7`。用一个
默认行为与规格相悖的库，等于给自己留一个必须记得关掉的开关。

**否决**：papaparse（默认 `dynamicTyping` 与规格冲突，且体积远超所需）。

---

## R5. 序号池的当前值：推导 + 下限，而非纯存储

**现状**：今天没有 `sequences` 表。当前号码由 `SequenceAllocator.#highestConsumed`
**从任务历史推导**——扫描该模板下所有已排队/打印中/已完成/已失败任务的 `seq_ranges`
取最大值。它的优点是不存在第二份状态可以漂移：号码印在标签上，而标签由任务记录。

**问题**：纯推导无法满足 FR-006 的「重置」——重置意味着把当前值改小，而推导值来自
历史，改不动。

**结论**：序号池存一个 `floor`（下限）字段，当前值取 `max(floor, 已消耗最大值)`。
重置即把 `floor` 设为目标值。历史仍是号码的唯一凭据，`floor` 只是一条「从此处重新开始」
的声明。

**附带修正**：推导的过滤条件从 `template_id` 改为池 id，因为池可被多个模板共用（FR-005）。
这使扫描无法再靠 `template_id` 索引收窄。**落地形态**：新建 `job_sequence_claims` 表
（`job_id`、`pool_id`、`start`、`end`、`step`、`digits`，`pool_id` 建索引），并**删除**
既有的 `print_jobs.seq_ranges` JSON 列——保留它等于让两处都记录号码、都可能被写，而
它们不一致时无从判断哪个印在了实物上，正是本条否决独立计数器的同一条理由。详见
`data-model.md` 的 `JobSequenceClaim`。

**否决**：纯存储的计数器（一旦与历史不一致，无法判断哪个才是真的，而错的那个会导致
重号）；删除历史来重置（历史是补打与追溯的依据，不能为了改一个数字而丢掉）。

## R6. 流式渲染：端口改为「总数 + 按序取页」

**结论**：`PrinterDriver.printPages` 的第一个参数由 `BinaryBitmap[]` 改为

```
{ total: number; at(index: number): BinaryBitmap }
```

**理由**：驱动需要**提前知道总数**——TSPL 的 `PRINT`、进度上报、以及「已印张数」都要
它；而页面本身应当按需生成。`Iterable` 无法提供总数，`AsyncIterable` 会把整条打印路径
异步化（队列、三个驱动、以及 `renderPage` 回调），改动面远大于收益，因为渲染本身是同步的。

`at(index)` 也让**补打**天然可行：补打的是同一批中的某一段，按下标取即可。

**影响面**：四个驱动（精臣、ZPL、dry-run、搁置中的 TSPL）、`PrintQueue`、
`buildJobPages`、以及 `contracts/driver-port.md`。这是宪章约束的端口契约变更，
必须同步更新契约文档。

**否决**：`Iterable<BinaryBitmap>`（无总数）；`AsyncIterable`（异步化整条路径）；
保留数组并只提高上限（12MB 位图同时驻留，且第一张标签要等全部渲染完）。

## R7. 行值的存储形状

**结论**：`data_source_rows` 一行一条记录，列值存为 JSON 对象（`{"列名":"值"}`）。

**理由**：列名来自 CSV 表头，是任意中文字符串（FR-009a），不能作为 SQL 列名；且替换
数据源时列集会变（FR-021a）。JSON 让「列」成为数据而非模式，替换只是重写行。10,000 行
× 若干列在 SQLite 中是几 MB，分页查询靠 `LIMIT/OFFSET` 加行序索引即可。

**否决**：宽表（列名不可控、替换即改模式）；键值三元组表（行数 × 列数 = 十万级记录，
且取一整行要聚合）。

## R8. 任务快照携带行值

**结论**：`snapshot` 增加 `rows: Array<Record<string, string>>`，按打印顺序排列。
`irForCopy(job, index)` 由 `rows[floor(index / copies)]` 取值，与序号值合并。

**理由**：FR-039/FR-040 要求任务自包含。上限 1000 张意味着单条快照最多约 1000 行值，
数量级是几百 KB。

**已知代价**：任务表随使用增长。规格未要求清理策略，`spec.md` 的 Deferred 中记录了
这一点；本期不做，但选型上不排除将来把快照移出主表。

---

## R9. 行选择的紧凑表示

**结论**：

```
{ all: true } | { ranges?: [number, number][]; ids?: number[] }
```

行号为**表内序号**（1 起，按行序）。`all` 在服务端于提交时展开。

**理由**：FR-033 的三种选择方式（勾选 / 区间 / 全选）天然映射到这三种形态，X-Y 输入
不必先展开再压缩。

**否决**：行 id 数组（5000 行即几百 KB，且丢失「全选」意图）。

## R10. 前端表格：`@tanstack/react-table` + shadcn

**结论**：新增 `@tanstack/react-table` 依赖，配 shadcn 的 Table 原语。

**理由**：`@tanstack/react-query` 已在依赖中，同一家的表格库在心智与版本管理上一致；
shadcn 官方的 data-table 范式正是这两者的组合，符合宪章「UI 组件一律优先 shadcn/ui」。

**用途有二且要求不同**：数据源管理页（可编辑单元格、增删行、粘贴）与打印对话框的行选择
（只读、分页、勾选、区间）。两者共用列定义与分页，不共用编辑能力。

---

## R11. 剪贴板粘贴：取 `text/plain`

**结论**：读取 `text/plain`，按制表符分列、换行分行。不解析 `text/html`。

**理由**：Google 表格与 Excel 复制时都会同时提供 `text/plain`（TSV）与 `text/html`
（一张表格）。TSV 已经是我们要的形状；解析 HTML 需要处理合并单元格、嵌套元素与样式，
换来的只是「保留格式」——而 FR-024 规定一切皆文本，格式本就不保留。

**已知限制**：单元格内含换行的内容在 TSV 中会被引号包裹，需按 CSV 的引号规则处理；
此逻辑与 R4 共用。

**否决**：解析 `text/html`（复杂度换不来价值）；要求用户先存成文件（FR-025 明确要求
免文件）。

## R12. 测试分层

沿用宪章的既有分层，不新增测试项目：

| 层 | 内容 |
|---|---|
| `default`（纯 Node） | 解析器、CSV 解析、编码/分隔符探测、行选择展开、序号推导、快照解析 |
| `web`（DOM） | 数据源管理页、行选择界面、粘贴、编辑器中的引用输入与阻塞提示 |
| `hardware` | 无新增 |

**每一个新增的可导航页面（数据源列表、数据源编辑）MUST 具备渲染断言**（宪章原则 II）。
