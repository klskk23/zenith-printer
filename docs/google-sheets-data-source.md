# Google Sheets 数据源（设计共识）

本文是一次完整访谈的结论，供 `/speckit.specify` 使用。它记录**决定了什么**、
**否决了什么**、以及**为什么** —— 后两者比第一者更容易在实现中被重新发明。

延续对象：003 里搁置的「Google Drive sheet 功能」。数据源的其余部分（`${}` 引用、
行选择、快照、流式渲染）全部沿用，本文只谈行从哪里来。

---

## 1. 授权机制：服务账号，不是 OAuth2

最初的设想是 Google OAuth2。它在这个部署形态下走不通，三条各自独立的原因：

**重定向回不来。** Google 对「Web 应用」类型的客户端只接受 HTTPS 重定向 URI，
唯二例外是 `http://localhost` 和 `http://127.0.0.1`。本服务跑在
`http://<局域网 IP>:3000`，同事的浏览器完成授权后无法跳回来 —— 那个重定向 URI
在 Google 后台根本注册不上。曾经的手工复制粘贴流程（OOB）已被 Google 下线。

**刷新令牌会过期。** 应用处于「测试」发布状态时，刷新令牌 7 天失效。Sheets 读取
属于敏感权限，转「正式」要走应用验证；免验证的只有「内部」用户类型，而那需要
Google Workspace 账号。

**授权面过大。** `spreadsheets.readonly` 授予的是那个账号 **整个 Drive** 的读权限。
本服务无鉴权、绑在 `0.0.0.0`，把这样一份授权放进来，影响范围远大于「读一张表」。

**结论：用服务账号。** 把需要的表分享给机器人邮箱
（`xxx@xxx.iam.gserviceaccount.com`）。没有同意屏、没有重定向 URI、没有 7 天失效、
不需要应用验证；而且它**只能看见被显式分享的那几张表** —— 影响范围恰好被「你分享了
哪几张」限死。代价是磁盘上多一份长期密钥，且每张新表都要手动分享一次。

> 上述关于 Google 政策的陈述来自访谈时的既有知识，政策会变。**落地前请对着当前
> 官方文档核实**，并确认在项目里启用 Sheets API。

### 凭据存放

密钥走**环境变量指向文件路径**，与 `ZENITH_HOST` 同一类。界面只读地显示
「已配置 / 未配置」和机器人邮箱 —— 人必须知道该把表分享给谁。

界面上**不提供上传入口**。设置页已明写「服务端配置由部署方式决定，界面上不提供」，
而这台服务无鉴权：一个接收私钥的接口等于给局域网上任何人开一个上传口。

密钥**绝不能进日志**。宪章 V 允许 debug 级导出协议帧，这条路径必须把密钥排除在外。

## 2. Google 登录：另立功能，不在本次范围

访谈中提出过「顺便用 Google OAuth 做登录」。技术上可行（OpenID Connect，只要 ID
token，不需要刷新令牌，所以 7 天那条不影响）。**但它撞的是同一堵墙，而且墙被挪到了
所有人的必经之路上**：读表失败只是某张数据源不能用，登录失败是谁都进不来。

翻过这堵墙只有一条不违背「不暴露公网」的路：给服务一个**真域名 + HTTPS**（内网 DNS
解析到局域网 IP，证书走 Let's Encrypt 的 DNS-01 挑战）。代价是域名、DNS 控制权、
证书续期、反向代理或进程内 TLS。

两点结论：

- **这是两个功能。** 捆在一起会让 Sheets 被域名和证书卡住，而它本来不需要。
- **即使做了登录，读表也不该复用登录者的授权。** 打印队列在无人登录时也要跑，那就
  仍需存刷新令牌；那份令牌授予的是那个人整个 Drive 的读权限；人一离职或撤销授权，
  依赖那张表的打印就断了。机器人的访问权不该挂在某个人的在职状态上。

`docs/design-consensus.md` 里「认证后续再做」是已记在案的待办，值得独立立项。

## 3. 同步模型：可刷新的链接

数据源记住 spreadsheet 与工作表，**行仍然存在 SQLite 里**，刷新时整表替换。

这样打印不依赖外网，现有的渲染、`PageSource`、提交时快照（FR-039）一行不用改。

### 链接的表在本地只读

否则有两个主人：本地改一笔，下次刷新被抹掉，而人不知道。编辑要回 Google 那边做。
现有的「替换」（上传新 CSV 覆盖）对链接的表同样应当关闭。

### 否决：一次性导入

读一次、变成普通数据源、不记来源。改动最小，但表一改就得重导一遍 —— 而「想用 Sheets
而不是重传 CSV」的动机多半正是不想记这件事。

### 否决：打印时实时读

不存行，预览与提交时现去 Google 取。数据永远最新，但打印变成依赖外网的操作：Google
不通、配额用尽或延迟高的时候，失败发生在人已经站在打印机前的那一刻。

---

## 4. 刷新时机：只手动

**不做定时自动刷新。** 表会在没有任何人操作的时候变；如果正好发生在有人看着行列表时，
序号会在他眼皮底下重排。

刷新入口有两处：数据源页，以及**打印对话框内**（需要新鲜数据的那一刻就在手边）。

### 按下刷新会清空当前的行选择

行选择是按序号做的（支持填 X-Y 区间）。刷新后那些数字指向的已经不是同几行 ——
留着比清掉更危险。

### 定时刷新交给部署方

产品内不做，但 CLI 提供 `data-source-refresh`。愿意上 cron 的人自己上，产品不替
所有人决定。

---

## 5. 范围指定：粘 URL + 选工作表 + 预览确认

从粘贴的链接里提取 spreadsheet id，列出工作表让人选，默认**首行为表头**。

**创建前先展示识别到的列名和前几行，确认后才落库。** 表头不在首行的表当场就看得
出来，而不是到打印时才发现有一列叫「本月出货清单」。

### 取值一律用 `FORMATTED_VALUE`

单元格里显示成什么，标签上就印什么。`UNFORMATTED_VALUE` 会把 `007` 变成 `7`、把
日期变成序列号 —— 正是 CSV 导入器明确拒绝的那类损失（FR-024）。

### 暂不支持 A1 区间

`Sheet1!A3:F` 能处理「上方有标题行、右侧有草稿列」的真实表格，但只对少数表有用，
且以后再加不需要改存储结构。先靠预览确认让人发现问题。

---

## 6. 失败与变化

### 刷新失败：保留上一次的行

网络不通、表被删、分享被撤销、工作表改名 —— 都保留旧行，说清原因，**不阻止用旧数据
打印**。

### 超出行数上限：拒绝这次刷新

数据源上限 10,000 行。超了保留上一次的行，与 `CSV_TOO_MANY_ROWS` 一致。

**不截断。** 截断的后果是打了 1~10000 行的标签，而 10001 行之后的存在与否无人知晓 ——
这比数据陈旧糟得多。

### 表头变化：加列直接应用，减列或改名要确认

设计里写的是 `${订单号}`，列名就是引用名。

- **新增列**：直接应用，伤不到任何设计。
- **减列或改名**：停下来确认，并**列出会受影响的设计**。

确认弹窗被随手点掉时，兜底仍是既有的 `bindingIssue`（读时计算，卡片与设计页长期
可见），而不是指望那一次点击。

---

## 7. 测试：默认套件必须脱网可跑

Sheets 客户端放在一个**端口（port）**后面，像打印机驱动那样有假实现。真实网络调用
只出现在 `hardware` 测试项目里。

不这样做，整套测试就得联网，而且会因为别人改了一张表而变红。

---

## 8. 范围

**Web**：链接、预览确认、刷新、解绑、只读提示、表头变化确认。

**CLI**：只加 `data-source-refresh`，走 REST。链接那一步的关键是人看一眼列名再点头，
命令行做不好这件事；而刷新命令把「要不要定时」交还给部署方。

CLI 走 REST 而非直连数据库，与 `template-import` 同一套做法：刷新逻辑只有一份实现。

---

## 9. 明确不做

- Google OAuth2（读表用服务账号）
- Google 登录 / 服务自身的鉴权（另立功能）
- 定时自动刷新（产品内；CLI + cron 是部署方的选择）
- 写回 Google 表
- A1 区间指定（以后可加，不改存储结构）
- 公开链接 / API key 读取公开表
- 把行数据写进模板导出文件

## 10. 对现有产物的影响

| 处 | 影响 |
|---|---|
| `data_sources` 表 | 新增来源相关字段（spreadsheet、工作表、上次刷新时间）；需要迁移 |
| 数据源编辑页 | 链接的表进入只读态；「替换」入口关闭 |
| 打印对话框 | 增加刷新入口，且必须在行选择器渲染之前生效 |
| REST 契约 | 新增链接、预览、刷新端点；错误码若干 |
| 新端口 | Sheets 客户端 + 假实现 |
| CLI | 新增 `data-source-refresh` |
| 环境变量 | 新增密钥文件路径 |

## 11. 待确认与风险

| 项 | 说明 |
|---|---|
| Google 政策 | 第 1 节关于重定向 URI、7 天刷新令牌、敏感权限验证的陈述需对着当前官方文档核实 |
| 服务无鉴权 | 本功能不引入这个问题，但它把 Google 上的数据搬进了局域网这条边界之内 —— 任何人都能刷新、也能读到行。这是「登录」应尽早排上的理由 |
| 密钥泄露面 | 服务账号密钥若泄露，能读所有被分享给它的表。文件权限要收紧，且绝不进日志 |
| 合规 | 把业务表分享给一个服务账号，是否满足数据合规要求，需要业务侧确认 |
| 名称来源 | 链接的数据源默认叫什么（工作表名？spreadsheet 名？）尚未定，规格里需要明确 |
| 配额 | 手动刷新的频率远低于 Sheets API 限额，但规格里应写明限流时的表现（归入「刷新失败」） |

### 与本文的两处偏差

**联网核实改为手工，不做成测试。** 本文第 7 节原话是「真实网络调用只出现在 hardware
测试项目里」。分析阶段发现宪章的「测试 MUST 确定性：禁止依赖真实时钟、随机数或**网络**」
是无条件的，而其隔离条款只为「需要**真实硬件**的测试」开口，措辞未涵盖外部网络服务。
两点核实因此移到 `quickstart.md` 第五节的手工验收——它们核实的本就是**关于 Google 的
事实**，不是本系统的行为。

**仓库没有 README.md**，本文第 1 节提到的部署说明落在 `.env.example` 与
`quickstart.md` 第一节，未新建 README。
